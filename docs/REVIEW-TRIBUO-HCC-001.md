# REVIEW-TRIBUO-HCC-001 — HCC / Universal Attribute Registry / Buyer Profile compatibility

**Date:** 2026-11-12  
**Status:** TECHNICAL REVIEW / S0-S2 INPUT, not an implementation or measured ML performance result.  
**Source baseline:** [UCE-001/002/003](DEC-UCE-001-UNIVERSAL-CLASSIFICATION.md), [ADR-003](ADR-003-JAVA-ML-RECOMMENDATIONS.md), [master requirements](REQUIREMENTS.md), [Reverse Marketplace](DEC-KILLER-FEATURES-R1.md).

**Technical decision:** retain HCC for taxonomy, Universal Dictionary for attribute definitions/controlled values, and explicit `FeatureSchemaVersion` as adapter to Tribuo. **Do not use numeric dictionary codes or a concatenated HCC numeric value directly as an ML continuous variable.**

## 1. Official Tribuo facts verified

- Tribuo represents input as named numeric features (`Feature(String,double)`), supports sparse feature spaces; internal feature IDs are managed by Tribuo. See https://github.com/oracle/tribuo/blob/main/docs/FAQs.md and https://tribuo.org/learn/4.3/docs/architecture.html .
- An `Example` is paired with a typed `Output`, and a `Model` consumes examples and produces typed `Prediction` objects. Dataset statistics, feature/output domains and provenance are integral to the lifecycle. https://tribuo.org/learn/4.3/docs/architecture.html
- Tribuo records feature names in lexicographic order internally; this **does not** imply that HCC numeric positional digits or a custom array slot map constitute the model's actual feature IDs. https://github.com/oracle/tribuo/blob/main/docs/Internals.md
- The docs warn that a prediction with no overlapping features can fail; some unseen features may be dropped. Therefore an application-level schema/version and coverage threshold is required, even if Tribuo accepts an example with partial overlap. https://github.com/oracle/tribuo/blob/main/docs/FAQs.md
- Tribuo supports feature hashing as an optional transformation, with possible collisions. It does not make MD5 output into a meaningful numerical taxonomy metric. Its docs prefer protobuf model serialization over deprecated Java object serialization. https://tribuo.org/learn/4.3/docs/architecture.html

## 2. Review matrix

| Design item | Verdict | Qualification |
|---|---|---|
| HCC fixed-width path codes | FIT | String-coded structured ancestry, parent links, stable identity. No arithmetic on path codes. |
| Universal BIGINT generated dictionary IDs | FIT | Stable identifiers only; not continuous ML values. |
| Global COLOR/MATERIAL/BRAND dictionaries | FIT | Canonical IDs and translation synonyms reusable across categories. |
| SIZE / SIZE_SYSTEM | FIT WITH CONDITION | Size number must be qualified by applicable system/unit/category, e.g. footwear 42 vs apparel 42. |
| Class attribute rules and valid combinations | CRITICAL | Typed validation + ontology before learning; never eagerly materialize all permutations. |
| Decimal measurement attributes | FIT | Normalize dimensionally compatible units, missingness and scale. |
| HCC fixed ML feature slot order | FIT WITH CONDITION | Freeze feature-name vocabulary and encoding schema. Tribuo uses feature names, so arrays are optional export format, not source of truth. |
| City / territorial code | FIT WITH CONDITION | City as categorical/territorial coverage match, not numerical KATO distance. Request destination takes precedence over residence. |
| Birth year | OPTIONAL / HIGH PRIVACY COST | Prefer optional coarse age bands; validate purpose/consent, minors, legal review, and incremental model uplift before use. |
| Customer behavioral segment | FIT WITH CONDITION | Only consent-eligible events; retain as-of, retention, provenance and segment version. |
| Tribuo prediction as deal eligibility | DOES NOT FIT | Eligibility belongs to deterministic product/seller/region/stock rules. |
| Single model across all product/service categories | HIGH RISK | Cross-domain attribute sparsity and label imbalance; use shared registry + shared feature schema core, with category-family-specific feature groups and models when justified. |

## 3. Canonical three-layer encoding

**Layer A — durable taxonomy and dimensions:** `DictionaryNode(id BIGINT, stableCode, kind, parentId)`, `ClassificationPath(code CHAR/VARCHAR, revision, nodeId)`, globally reusable typed `AttributeDefinition`, enum option dictionary, applicability `ClassAttributeRule`, and verified Seller SKU / Service Spec facts. Numeric ID remains generated by the database; published hierarchy code remains string padded and versioned. Do not embed volatile SKU price or city residency into HCC taxonomy code.

**Layer B — match evidence (deterministic):** buyer requirements + seller normalized offering, strict type/unit/value comparison, own seller, public listing, delivery coverage, quantity, expiration and confirmed all-in costs. Output `MatchEvidence` with per-attribute status (`EXACT`, `COMPATIBLE`, `MISSING`, `REJECTED`) and reason codes; any failed hard constraint prevents ML scoring.

**Layer C — model-specific Tribuo features:** immutable `FeatureSchemaVersion` mapping evidence + permissible buyer behavior into named doubles (one-hot categories, continuous measurements, masked missing data), with trained `ModelVersion` artifact manifest. Optional `double[]` interchange has a frozen feature-name-to-index mapping, never raw HCC digits.

### Example: buyer requests 256 GB phone, seller offers a variant

```text
HCC path              = "01020030012300000001"  (illustrative)
category ancestry     = category.01=1; category.01.02=1; category.01.02.003=1
brand from dictionary = attribute.brand.SAMSUNG=1
storage               = attribute.storage_gb=256
required-match        = match.model_exact=1; match.storage_exact=1
territory             = fulfillment.same_city=1; fulfillment.coverage_eligible=1
deal terms            = price.budget_deviation_pct=-3.125; delivery.quoted_days=2
missing flags         = delivery.fee_known=1; seller.reliability_known=1
optional behavior     = buyer.affinity.smartphones=0.8 (only if permitted)
```

Never feed the raw concatenated HCC value, numeric `brandId` or KATO territory code as a scalar expected to convey ordering or distance. Never fabricate delivery cost or stock availability.

### Baseline model grouping

- **SellerResponseModel:** predict response within a declared response window for *actually delivered* eligible buyer-demand invitations, with censored/incomplete-window rows excluded.
- **BuyerChoiceModel:** predict qualified buyer selection after an *actual offer impression*, with a properly defined outcome window and debiasing for exposure/position (not every unseen offer is a negative).
- **SmartDealFinder:** deterministic safe cost comparison before ML; ranking model may use its verified evidence.
- **BuyerSegmentation:** start with interpretable aggregate interest categories and stable consent-controlled derived features. Do not claim predictive performance of age/city without controlled evidence.
- **Cold start:** rules + verified price / fulfillment comparisons; don't train fake examples and deploy model as factual scores.

## 4. Strict feature schema for reproducibility

A feature schema entry should contain:
`{featureName, sourcePath, type, encoding, orderedSlot?, categoryVocabularyRevision?, unit?, normalizer?, missingPolicy, featureScope, purpose, applicableClasses, sensitivity}`.

Every training/inference artifact must identify:
`{classificationRevision, dictionaryRevision, featureSchemaVersion, featureVocabularySha256, encoderVersion, trainingAsOf, modelVersion, inputWindow, labelWindow, modelArtifactSha256}`.

Encoding invariant: **same normalized facts + same version → same ordered feature names and values**; deterministic hashing of canonical serialized schema allows equality check, not semantically useful feature values.

Handling schema drift:
- additive new dictionary enum values appear as unknown/missing under prior model vocabulary, with explicit coverage diagnostics; no silent new dense slot shift;
- rename translations does not change stable keys;
- edited class attribute semantics requires new schema revision and migration map; rebuild datasets/models as necessary;
- model loads only with matching compatible encoder manifest; otherwise fall back to verified deterministic rank.

## 5. Buyer city and birth year: governance and technical assessment

Buyer city is best as **two distinct concepts**:
`BuyerProfile.residenceCityAreaId` (optional, buyer-chosen; personalization only when allowed) and `BuyerDemand.fulfillmentCityAreaId` (per-request delivery eligibility). KATO/area parent graph provides same-city, same-region and coverage conditions; numeric code subtraction does **not** represent geographic proximity.

Birth year is self-declared and optional; `asOfYear - birthYear` yields approximate age and can be off by one. Coarse age brackets may support legally permitted adult opt-in segmentation, but are **not** a hard eligibility gate, and should be withheld for marketing to minors pending child safety/legal review. Treat unknown/withheld separately. A model without these personal dimensions should be the default baseline; only add them if an A/B study shows material benefit and legal review permits it. No profile data leakage into seller notifications.

Never include phone number, full street address, exact GPS, login secrets or free-form private messages as raw model features.

## 6. Blocking S2 findings

1. **Taxonomy identity/coding:** confirm HCC digit-width capacity/overflow, source of issued segment IDs, parent/reparenting mapping, and immutable path aliases; don't store zero-padded path as BIGINT.
2. **Dictionary rules:** choose an enforced typed-value physical schema (FK and check constraints), a versioned category→attribute applicability relation, separate translations, normalized unit standards and governed synonyms.
3. **Schema split:** define global ML feature names versus class-specific feature families; cap vocabulary cardinality, protect rare identifiers and prevent exploded one-hot vectors for unique listing IDs.
4. **Temporal training:** exact impression/invitation events, as-of features, outcome windows, delayed feedback, train/test chronology, exposure bias and class weighting.
5. **User privacy:** binding purposes/retention, consent revocation, no profiling minors, proper deletion/retraining policy and legal review.
6. **Model safety:** feature coverage threshold, model artifact signature/hash, deterministic fallback, rollback, inference latency and observability; do not make commercial actions depend on ML.
7. **Performance:** separate matching query constraints and indexes from training workloads; benchmark candidate count (100/1000/10000), sparse feature size, time to encode/rank and PostgreSQL I/O.

## 7. Acceptance tests proposed

- TRH-01: known HCC and stored dictionary IDs map to one stable named feature space independent of translations.
- TRH-02: new dictionary enum value cannot alter existing feature positions without vocabulary revision.
- TRH-03: low-level numeric dictionary code differences cannot affect distance/score except via explicitly defined categorical features.
- TRH-04: same encoded fact snapshot at training and inference produces bitwise-identical named feature ordering and equal numeric values.
- TRH-05: training dataset contains only decision-time facts, eligible impression events and completed label windows.
- TRH-06: SKU 128GB rejected against hard 256GB demand before Tribuo, even if model predicts high probability.
- TRH-07: a seller outside requested delivery city cannot be invited solely due to ML score.
- TRH-08: null/unknown/withheld user birth year remain distinct; no personalized age-based marketing for minors.
- TRH-09: selected request city controls delivery applicability even if profile residence differs.
- TRH-10: expired model/encoder or low overlap falls back to safe deterministic ranking with an observable reason.
- TRH-11: comparison excludes unknown/unquoted shipping from "cheaper all-in" result.
- TRH-12: evaluate models against deterministic ranking using chronological holdout, PR-AUC, Precision@K, calibration and operational complaint/opt-out controls.

## 8. Overall judgment

**Architecture fit: GOOD (conditional)**, not a measured metric. Main strengths: consistent identifiers, reusable typed attributes, explainable hard matching, reproducible features and modular Java-only integration. Main weaknesses to resolve before implementation: rigid HCC digit limits, attribute polymorphism/integrity, schema drift, service-specific semantics, sparse high-cardinality data, label quality and profiling governance.

**Next development slice:** two verticals (smartphones, electrician services), frozen `FeatureSchemaVersion` and `MatchEvidence` records, pure-Java schema/encoder unit tests; then PostgreSQL typed dictionary and Testcontainers. Introduce Tribuo dependency/training after the encoding contract passes S2 review and actual outcome data can be observed.
