# ML-R3.0 — authenticated exposure evidence and point-in-time labels

**Branch:** `docs/adr-002-jpa-architecture-review`. **Release:** HOLD / RESEARCH_ONLY.
**Scope:** first reproducible PostgreSQL 17 dataset slice for `seller_response_24h`.
**Out of scope:** automated seller UI, human-view verification, ML training, model promotion.

## 1. Why queue delivery is not a training exposure

`ml_seller_invitation_inbox.delivered_at` means a record is accessible in the
seller's **internal** inbox. It is not a seller push delivery, impression,
opening of a page or human observation. A trainable exposure is recorded
separately by an authenticated and consent-authorized seller action.

`POST /api/v1/sellers/{sellerId}/invitations/{invitationId}/view`:
- Available only when `zakaz.ml.r3.exposure.enabled=true`,
  `zakaz.ml.r2.consent-api.enabled=true`, and
  `zakaz.seller.bid-workspace.enabled=true`.
- Requires `SCOPE_deal:bid`, server-verified `SELLER_ADMIN`, correct seller
  ownership, active two-sided opt-in and a currently actionable quote context.
- The client must submit POST **after actually presenting the invitation**;
  merely calling GET quote-context must not generate a view.
- First acknowledgement wins: immutable record and idempotent 204 retry.
  Buyer revocation / seller opt-out is serialized by PostgreSQL consent locks.
- The acknowledgement proves a valid authenticated request, **not** proof a
  human physically viewed the contents. Bot and unattended-session policies
  require a separate independent review.

## 2. PostgreSQL V30 evidence lineage

`V30__ml_r3_view_acknowledgement_and_consent_history.sql` adds:
- `ml_seller_invitation_view`, with a composite FK to a real, delivered
  invitation and server-stamped `viewed_at` / `recorded_at`, plus frozen
  `requested_lines` (no buyer contact data);
- immutable `ml_invitation_consent_audit`, populated by server DB triggers
  from buyer-demand sharing and seller in-app preference changes;
- append-only guards and indexes.

No historic views, account interactions, negative labels or consent periods
are backfilled or inferred. Existing ML-R2 trade event triggers remain
transactional and independently immutable.

## 3. Reproducible dataset contract

`MlSellerResponseDatasetBuilder.build(cutoff)` is read-only,
`REPEATABLE_READ` and uses one caller-specified UTC cutoff. It does not
publish a dataset to an external model service and does not execute in the
order transaction.

A candidate row requires an acknowledged view and real private inbox lineage.
The primary feature `requestedLines` is frozen at view time (v1).
A positive 24-hour label requires a real `seller_bid_snapshot`, immutable
`bid_quote_snapshot` and a committed `ml_trade_event` ingested no later
than cutoff, submitted **after** the view and no more than 24 hours later.
Untrusted client-side events cannot create training labels directly.

The builder emits a deterministic, ID-sorted list of typed samples and a
SHA-256 digest over the schema version, exact cutoff and canonical rows.
Rebuilding the *same* temporal snapshot must produce identical rows and
digest. A new cutoff is a **new** snapshot, never a silent rewrite.

## 4. Safe label states and deliberate readiness gate

| Result | Condition |
| --- | --- |
| `POSITIVE / VALID_BID_WITHIN_24H` | Committed valid seller quote + bid with event ingested before cutoff |
| `CENSORED / INCOMPLETE_24H_HORIZON` | Exposure window has not matured |
| `CENSORED / CONSENT_REVOKED` | Buyer or seller revoked opt-in during the observation period |
| `CENSORED / DEMAND_EXPIRES_EARLY` | Request expires before a complete 24-hour observation |
| `CENSORED / UNVERIFIED_CONTINUOUS_ELIGIBILITY` | Seller/catalog/stock historical eligibility is not fully certified |

**No negatives are generated by ML-R3.0.** Historical seller membership,
catalog changes, inventory availability and delivery-area eligibility do
not yet have a complete, certified, 24-hour as-of audit. Asserting the seller
*chose not to respond* would therefore be unsafe. Every result returns
`trainable=false` and `BLOCKED_NO_VERIFIED_NEGATIVE_LABELS`.

The positive/censored dataset is useful for verifying **telemetry provenance,
latency, event ordering and response attribution**; it cannot yet prove
predictive lift and must not be used to promote an ML model.

## 5. CI and quality gates

PostgreSQL Testcontainers acceptance:
- An inbox message or GET quote-context **does not** imply view.
- Authenticated POST is scoped, real, immutable and idempotent.
- Consent revoke prevents new acknowledgement and censors the historical row.
- Real accepted HTTP bid after ack creates a positive observation.
- A bid before ack does not create a positive label.
- Data ingested after a pinned cutoff does not change its digest.
- Artificial historical test observations without continuous evidence remain
  censored; future cutoffs are refused.
- Old trade-queue tests continue working with real FK restrictions.

Synthetic timestamp modifications in test fixtures prove algorithmic safety;
they are not production source facts or business-uplift evidence.

## 6. Next qualification milestones

1. Seller UI: explicit view acknowledgement only after real invitation content
   is presented; real Keycloak seller E2E and anti-automation policy.
2. Historical eligibility changes: versioned, immutable membership/catalog/
   stock/territory observations to safely establish 24-hour nonresponses.
3. Persist a canonical, immutable dataset manifest (source watermark, source
   revision, code/schema SHA, row/digest counts, retention/lineage).
4. Real positive and negative cohort; chronological/embargoed holdout and
   subgroup analysis, then one offline Tribuo candidate against an independent
   deterministic baseline. No activation without measured incremental uplift.
5. Independent S2, GDPR/KZ privacy and retention review, multi-pod replay/DB
   contention tests, 5k load gate. `main` merge remains prohibited without
   separate approval.
