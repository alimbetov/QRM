# QRM — консолидированное техническое задание v1.3

**Дата:** 2026-11-12 · **Статус:** Product baseline / архитектура на проектировании (не утверждённый релиз)  
**Первый рынок:** Казахстан · **Валюта:** KZT · **Интерфейсы:** React Web + Flutter Android/iOS  
**Подход:** modular monolith, domain boundaries, scenario-first, test-first.

## 1. Цель и границы

QRM — платформа прямой торговли по QR-кодам. Продавец регистрируется, оформляет профиль (название, никнейм, логотип), публикует товары/услуги/цифровые предложения и распространяет QR. Покупатель без входа видит страницу React, цены, ролик YouTube, рейтинг и просмотры; может оставить Web-заявку с телефоном и желаемой ценой. Flutter обеспечивает полноценные заказы, переговоры, избранное, уведомления, получение и отзывы. Оплата происходит **напрямую между сторонами**: QRM не принимает, не резервирует и не возвращает деньги.

MVP не включает эквайринг, мультипродавцовую корзину, собственную курьерскую сеть, ERP, ML-рекомендации и микросервисы. **Web-заявка (lead) — не подтверждённый заказ** и не резервирует товар.

## 2. Роли и регистрация

- `GUEST`: просмотр PUBLIC/UNLISTED по URL, Web-заявка с контактным телефоном и согласием на обратный звонок, без избранного.
- `BUYER`: Flutter-заказы, согласование цен, отслеживание цен по избранному, подтверждение получения, претензии и отзывы.
- `SELLER`: Flutter-профиль/логотип, объявления, цены, акции, QR, Web-заявки, заказы и аналитика.
- `ADMIN`: модерация, категории, злоупотребления, аудит.

Один аккаунт может иметь несколько ролей. Регистрация: телефон + OTP, уникальный никнейм; email необязателен, подтверждается при использовании. Язык RU/KK/EN/ZH. Разделять идентичности покупателей и продавцов запрещено.

### 2.1 SellerProfile

`sellerId, userId, nickname, displayName, publicSlug, logoMediaId?, description?, status, timestamps`. Один профиль на аккаунт в MVP. Логотип опционален, допустимы PNG/JPEG/WebP; максимум 5 МБ, рекомендуется квадратное изображение. Backend проверяет фактический формат и генерирует варианты; отсутствие логотипа → инициалы. Логотип связан с профилем и автоматически виден во всех объявлениях. Публичная страница `/s/{slug}` показывает продавца, рейтинг и активные объявления; QR может ссылаться как на профиль, так и на конкретное объявление.

## 3. Каталог и объявления

**Product** — классифицированная сущность/характеристики товара. **Listing** — предложение конкретного продавца с собственными условиями. Типы: `PHYSICAL`, `SERVICE`, `DIGITAL`. Категории и их иерархия берутся из модерируемого справочника; отсутствующую категорию продавец предлагает на рассмотрение.

Поля публикации: продавец, категория, тип, название и описание хотя бы на одном из RU/KK/EN/ZH, 3–5 фотографий, единица измерения, базовая цена в KZT, статус. Опционально: одна YouTube-ссылка, характеристики, остаток, минимальный объём и условия исполнения. Услуга использует дату/место/порядок оказания; digital — способ предоставления доступа вместо физической доставки.

**Локализация (DEC-09A):** разрешена публикация на одном языке; недостающий перевод отображается с fallback на исходный текст; машинный перевод предлагается опционально и не перезаписывает подтверждённый продавцом перевод. Все четыре языка доступны для редактирования.

**Медиа:** 3–5 фото обязательны к публикации (для черновика меньше допустимо), порядок и главное фото, S3-совместимое хранение, thumbnails, MIME/content inspection, удаление EXIF. YouTube URL нормализуется к video ID и валидируется по allowlist, iframe загружается по требованию.

### 3.1 Состояния Listing

- `DRAFT` — только владелец; недоступен для новых заказов.
- `PUBLIC` — публичная страница, каталог, QR, заявки/заказы.
- `UNLISTED` — прямая ссылка/QR, нет в публичном каталоге; ссылка **не секретна**.
- `ARCHIVED` — нет новых заявок и заказов, история сохраняется, QR даёт страницу недоступности.

Переход в PUBLIC/UNLISTED возможен только после валидации публикации. Архивирование не меняет созданные ранее заказы.

## 4. Цена, количество, скидки

Единицы измерения через контролируемый справочник: `PCS, G, KG, ML, L, M, M2, M3, HOUR, SERVICE` (для digital предусмотреть `LICENSE`/доступ после доменного решения). Штучные товары — целые количества, остальные могут иметь Decimal scale. Цена вычисляется на сервере точной десятичной арифметикой (BigDecimal); валютная точность и округление определяются политикой KZT.

Для Listing задаётся **базовая цена** и до **четырёх дополнительных PricingTier** с `minQuantity, maxQuantity?`, типом `FIXED_UNIT_PRICE | DISCOUNT_PERCENT` и значением. Диапазоны не пересекаются; последний может быть открытым.

**DiscountCampaign**: расписание начала/окончания с часовым поясом продавца (хранение UTC), область всего Listing либо конкретного диапазона, величина `FIXED_UNIT_PRICE | DISCOUNT_PERCENT`, состояния `SCHEDULED, ACTIVE, FINISHED, CANCELLED`. Наложение акций, дающих две действующие цены одному диапазону, запрещено в MVP. Порядок: выбрать tier → рассчитать обычную цену → применить одну текущую акцию → snapshot цены заказа. После подтверждения цена заказа неизменна. Истечение акции не пересчитывает старые заказы.

**PriceNegotiation**: покупатель может предложить цену; продавец `ACCEPT / REJECT / COUNTER`; предложение имеет срок действия, назначаемый продавцом. Максимум **5 раундов встречных предложений в одном согласовании (DEC-04A)**, раунды логируются. После завершения можно создать новое согласование; повторные заказы одного Listing не ограничиваются, пока он доступен. Лимит относится к переговорной сессии, не к количеству заказов. Предложение нельзя принять после expiry или после финализации.

## 5. QR и React Web

QR содержит **постоянный HTTPS URL**, например `/p/{publicId}`; код не хранит цену/описание. Можно создавать несколько source-tagged QR для одной карточки (витрина, упаковка, реклама) и QR профиля; скачать PNG/SVG. Изменение товара не ломает QR.

React Web без авторизации показывает: логотип и имя продавца, 3–5 фото, название/описание и fallback-перевод, обычную/акционную цену и срок акции, YouTube, рейтинг, **публичное число просмотров**, информацию о доступности, QR/source, кнопку открытия Flutter и Web-форму. **Серое сердце избранного в Web неактивно**; добавить в избранное можно только во Flutter. Universal Links / App Links ведут на то же объявление; fallback в магазин приложений, восстановление контекста после установки — отдельный проверяемый сценарий, без обещания безусловного deferred deep link.

### 5.1 Web purchase lead (DEC-01)

Гость оставляет `listingId, phone, quantity, preferredUnitPrice?, comment?, callbackConsent`. Это запрос обратного звонка, а не электронное согласование сделки. Цена может быть публичной (без торга) либо предложенной; нужно явно показать это различие. Покупатель предоставляет телефон для обратного звонка продавца. OTP для Web-заявки не обязателен; вводятся rate limit, антиспам, прозрачное согласие на передачу контакта продавцу и защита от использования чужих номеров. Backend не доверяет полям суммы, валидирует количество/цену/лимиты, записывает snapshot Listing и согласия. Состояния `NEW → VIEWED → CONTACTED | DECLINED | EXPIRED | WITHDRAWN`. Продавец звонит по указанному телефону при заинтересованности, а результат разговора отмечает вручную. Web-заявка сама по себе **не превращается автоматически в CustomerOrder**. Если стороны затем оформляют заказ во Flutter, он создаётся отдельно и может ссылаться на исходную Web-заявку. Продавец получает уведомление и **сам связывается с заявителем, если предложение его устраивает**. Не обещать ответа/резерва/покупки. Web-заявка заканчивается обратным звонком/обработкой продавцом; электронное подтверждение цены и создание заказа относятся к Flutter. Запрещено автоматически создавать заказ при получении Web-заявки. Телефон виден только уполномоченным лицам и хранится ограниченный срок; rate limit/anti-abuse обязателен.

## 6. Flutter

**Покупатель:** вход, карточки, избранное, отслеживание цены, push, оформление заказа (количество, адрес/дата для physical; специфические параметры service/digital), предложение альтернативной цены, история переговоров, доставка/получение, претензии, оценки и фотографии.  
**Продавец:** профиль/логотип, категории, объявления/медиа/переводы, цены и акции, QR-кампании, Web-заявки с обратной связью, согласование, исполнение и аналитика.

### 6.1 Избранное и уведомления

`Favorite` уникален по `(userId,listingId)`. Во Flutter выбирается `trackingMode = UNIT | QUANTITY` и `watchedQuantity`. Система сравнивает **эффективную цену для выбранного количества** с reference/last-notified, учитывает запланированные скидки, присылает push только при реальном снижении и согласии пользователя. Использовать FCM, NotificationPreference, PushDevice, Outbox и idempotent delivery; дедупликация, throttle, отказ от маркетинговых push и обработка невалидных токенов. Изменение цены/начало акции не должно блокироваться недоступностью FCM.

## 7. Заказ, исполнение, расчёты

**CustomerOrder** — отдельная сущность от Web Lead. MVP: один Listing на заказ, snapshot `seller, buyer, listing, type, quantity, unit, unitPrice, total, currency, discount/offer, terms, createdAt`. Для physical: адрес и ожидаемая дата; для service: дата и условия оказания; для digital: способ предоставления. Покупатель и продавец договариваются о взаиморасчёте напрямую; **система не фиксирует успешную оплату без подтверждённых внешних данных**.

Ортогональные состояния:
- Negotiation: `PENDING / COUNTER_OFFERED / ACCEPTED / REJECTED / EXPIRED`;
- Order: `PLACED / CONFIRMED / PROCESSING / COMPLETED / CANCELLED`;
- Physical delivery: `AWAITING_SHIPMENT / IN_TRANSIT / DELIVERED / FAILED` (+ `NOT_REQUIRED` для нефизических);
- Return/claim: `REQUESTED / APPROVED / REJECTED / RETURNED`.

Фактическая матрица переходов и роли акторов проектируются отдельно; запрещены произвольные PATCH статуса. Создание заказа и переходы статуса идемпотентны; конкурентное согласование — через version/locking. Отдельная history/audit; изменения Listing/скидки не изменяют confirmed Order.

**Возврат/претензия (DEC-06):** справочник причин + «Другое», текст и фото; правила для физического товара, услуги и цифрового продукта различаются. Решение о возврате денег не автоматизируется, учитываются права покупателей и применимое законодательство.

## 8. Рейтинги и отзывы

Рейтинг **товара** отделён от рейтинга **продавца**. После подтверждённого получения покупатель оценивает товар (1–5), может приложить текст и до 5 фото; один отзыв на Order/Listing с историей редактирования. Отмена до получения не даёт права оценивать качество товара, но может учитываться в метриках исполнения продавца. После получения и возврата отзыв допустим. Модерация и защита от дубликатов/накрутки обязательны.

## 9. Просмотры, QR-аналитика

События: `LISTING_VIEW, QR_VISIT, APP_OPEN, VIDEO_CLICK, ORDER_STARTED, ORDER_CREATED, FAVORITE_ADDED`. Публичный счётчик — агрегат засчитанных просмотров; владелец видит подробный breakdown по датам и QR-источникам (views, unique, lead, order, conversion). QR_VISIT означает открытие QR-ссылки, **не факт сканирования камеры**. Не считать React re-render, prefetch и ботов просмотрами. Уникальность — одна идентичность за скользящие 24 часа на Listing, с краткоживущим, приватным идентификатором; без постоянного fingerprint. Сырые события имеют retention. Ошибка аналитики никогда не блокирует показ объявления.

## 10. Безопасность, качество и ограничения

- AuthN + role/ownership/record-level AuthZ; запрет доступа к чужим контактам, черновикам, приватным аналитическим данным.
- OTP throttling, anti-spam на leads, idempotency keys для мутаций, строгая серверная валидация денег и статусов.
- Безопасная загрузка изображений, storage ACL, HTTPS, rate limits, audit, secrets вне Git.
- Постраничная выборка, N+1 контроль, observability с correlation IDs; резервные копии и проверка восстановления.
- Конфиденциальность телефона/адреса; минимизация и сроки хранения; отдельная правовая проверка Казахстана до production.
- НФ-требования **как целевые гипотезы**: p95 API чтения карточки ≤300ms, p95 создания заказа ≤800ms без внешних API при документированном профиле нагрузки; доступность 99.5%/месяц после запуска. Подлежат проверке.
- React UI не является boundary безопасности: Backend API проверяет пользователя независимо от клиента.
- Не обещать юридическую «прозрачность» без политики защиты данных, соглашения и проверки роли оператора.

## 11. Главный сквозной acceptance-сценарий

Продавец регистрируется → загружает логотип → выбирает категорию и тип → создаёт Listing, 3–5 фото, одну локаль, tier и timed discount → PUBLIC/UNLISTED → QR → анонимный просмотр React (в том числе YouTube, счётчик) → Web-заявка с телефоном для обратного звонка **или** переход в Flutter → избранное/price watch → падение цены и один релевантный push → предложение цены (≤5 раундов) → подтверждённый заказ со snapshot суммы → доставка/оказание/выдача → получение → отзыв с фото → аналитика продавца по QR и конверсиям.

## 12. Не включено в признание готовности

Этот документ фиксирует требования, но **не означает реализованную систему**. Code/CI/DB/mobile/web acceptance подтверждаются отдельно. Решения, требующие детализации, перечислены в `DECISIONS.md`; сценарии и gates — в `SCENARIOS.md`.

## 13. DEC-17 — согласование во Flutter и формирование заказа

**Web:** покупатель оставляет телефон и желаемую цену. Продавец, если заинтересован, звонит. Сам факт звонка или отметки о согласии в Web-заявке не создаёт заказ и не является автоматическим электронным акцептом покупателя.

**Flutter:** покупатель предлагает цену → продавец принимает, отклоняет или направляет встречное предложение (не более пяти раундов в рамках одной сессии) → согласованное предложение получает состояние `AGREED` → по явному действию оформляется `CustomerOrder`. В созданном заказе сохраняется snapshot согласованной цены, количества, единицы, KZT, участников и `acceptedOfferId`. На одну согласованную сделку — не более одной конвертации в заказ (уникальный ключ и транзакционная идемпотентность). `AGREED` не означает оплачено/доставлено.

## 14. DEC-18 — отзыв заявки, предложения и заказа покупателем

Покупатель может отозвать Web-заявку до закрытия её обработки (`WITHDRAWN`) через защищённую ссылку/проверку владения номером; отозвать активное, ещё не согласованное предложение во Flutter (`WITHDRAWN`); самостоятельно отменить `PLACED` заказ до подтверждения продавцом (`CANCELLED_BY_BUYER`). После подтверждения заказа создаётся `CANCELLATION_REQUESTED` и далее применяются бизнес-правила стадии исполнения и законные права покупателя; нельзя ограничивать предусмотренные законодательством Казахстана права на отказ. Причина — из справочника или текст, с аудитом и уведомлением продавца. Повторный заказ по активному объявлению разрешён. История не удаляется.


## 15. DEC-23 — закладки и прочитанные/непрочитанные обращения в кабинете продавца

Для **Web Seller Cabinet и Flutter Seller** поддержать личную закладку (bookmark / pinned) и состояние прочтения для трёх типов входящих записей: `PurchaseLead`, `PriceNegotiation` и `CustomerOrder`. Это **не** покупательское избранное товаров (`Favorite`) и не влияет на статусы сделки.

- `isBookmarked` отмечается/снимается вручную продавцом, не закрывает и не перемещает заявку в архив.
- `isRead` персонален для конкретного пользователя, обслуживающего аккаунт продавца; новый входящий объект по умолчанию непрочитан. Действие «Отметить прочитанным/непрочитанным» доступно вручную. Просмотр списка не отмечает запись прочитанной автоматически; открытие детализации может отмечать её прочитанной после успешной загрузки.
- При новом содержательном входящем сообщении, предложении цены или изменении заказа со стороны покупателя запись снова становится **непрочитанной** для продавца. Собственные действия продавца не должны порождать для него непрочитанное уведомление.
- Закладки не снимаются автоматически при изменении статуса или прочтении.
- Web и Flutter читают/меняют одно серверное состояние, синхронизированное между устройствами.
- Фильтры `ALL | UNREAD | READ | BOOKMARKED` могут сочетаться с типом, бизнес-статусом, периодом, Listing ID. Сортировка `lastActivityAt DESC, id DESC` и **cursor/keyset pagination**; limit по умолчанию 30, максимум 100; cursor непрозрачен и привязан к фильтрам и владельцу.
- Вкладки показывают счётчики непрочитанных отдельно по заявкам, предложениям и заказам, рассчитанные сервером. В MVP массовая отметка «Прочитать все» необязательна; если реализуется, должна быть ограничена явно выбранным фильтром и атомарной политикой cut-off.
- При отзыве заявки/отмене заказа отметки сохраняются для истории, но приватные данные и доступ контролируются текущими правами.

### Предлагаемые API

```http
GET   /api/v1/seller/inbox?type=LEAD&read=false&bookmarked=true&limit=30&cursor=...
GET   /api/v1/seller/inbox/unread-counts
PUT   /api/v1/seller/inbox/{type}/{id}/read-state
PUT   /api/v1/seller/inbox/{type}/{id}/bookmark
```

В `PUT` передаётся `{ "value": true|false }`. Идентификатор записи всегда проверяется на принадлежность/доступ продавца; повторное назначение того же значения идемпотентно.
